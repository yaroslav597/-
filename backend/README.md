# FastAPI ↔ pymavlink

Локальный backend-мост для текущего React-планировщика. Он сохраняет миссии, проверяет данные, компилирует MAVLink-команды, загружает их через протокол миссий и передаёт телеметрию по WebSocket. Отправка миссии не включает ARM и не запускает полёт.

## Запуск на Windows

Для обычной работы с уже установленными зависимостями запускайте [start-local.cmd](../start-local.cmd). Он поднимает Linux SITL в Ubuntu WSL, backend и React в фоне, ждёт подключения автопилота, открывает <http://127.0.0.1:5173/> в браузере и сохраняет логи в `.runtime/logs`. Выберите «Backend / MAVLink». После успешного запуска окно закрывается, а службы продолжают работать. При ошибке окно остаётся открытым с сообщением. Повторный запуск использует уже работающий экземпляр SITL и не создаёт дубликаты. Чтобы запустить без открытия браузера, используйте `start-local.cmd --no-browser`.

Нужен Python 3.12 или новее. Из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Команда uvicorn выше запускает только backend; для отдельного запуска интерфейса используйте `npm run dev`. Для общего запуска после установки SITL используйте [start-local.cmd](../start-local.cmd). API: <http://127.0.0.1:8000/docs>, состояние: <http://127.0.0.1:8000/api/health>.

Для воспроизведения проверенного окружения вместо диапазонов версий используйте `backend/requirements.lock.txt` (Python 3.12, Windows). В рабочей папке окружение уже подготовлено; `.venv`, локальный интерпретатор `.runtime` и база данных не включаются в Git.

В интерфейсе выберите «Источник телеметрии → Backend / MAVLink». «Сохранить на сервере» работает без автопилота. «Загрузить в автопилот» требует HEARTBEAT, HOME_POSITION и выключенного ARM. До подтверждения результат отображается как выполняющийся. При таймауте результат на борту неизвестен; автоматического повторного POST нет.

Сервер запускается одним процессом: один worker владеет одним MAVLink-соединением. Второй экземпляр сервера нельзя направлять на тот же автопилот. Этот этап рассчитан на локальную разработку, без многопользовательской авторизации.

## Подключение SITL

Общий запуск использует дистрибутив `Ubuntu-24.04` в WSL 2. Под обычным пользователем Ubuntu должен быть собран `~/ardupilot/build/sitl/bin/arducopter`. Подготовка окружения описана в [инструкции ArduPilot](https://ardupilot.org/dev/docs/building-setup-linux.html).

1. [start-local.cmd](../start-local.cmd) — запустить Linux ArduCopter с Home в Москве и TCP-портом 5760, backend с `MAVLINK_ENDPOINT=tcp:127.0.0.1:5760` и интерфейс React.
2. В React выбрать «Backend / MAVLink», дождаться подключения и Home, загрузить план и нажать «Проверить миссию на борту».

[Скрипт WSL](../tools/sitl_wsl.py) сохраняет параметры и данные симулятора в `~/.local/state/aero-sitl` внутри Ubuntu и держит открытым стандартный ввод дочернего процесса. Логи Windows: `.runtime/logs/sitl-wsl.out.log` и `.runtime/logs/sitl-wsl.err.log`. Запуск проверяет наличие сборки до остановки старых служб. При переходе с Windows SITL останавливаются только симулятор и backend этого проекта, при выключенном ARM и отсутствии активной операции. Миссию нужно загрузить в новый симулятор заново; ранее сохранённые задания остаются в базе backend.

Для другого имени дистрибутива: `powershell -ExecutionPolicy Bypass -File tools/start-local.ps1 -WslDistro Ubuntu`. WSL должен разрешать подключение Windows к Linux через localhost; в проверенном окружении это работает через `127.0.0.1:5760`. Проверено на Linux ArduCopter 4.8.0-dev: загрузка и обратное чтение двух тестовых миссий с RTL и LAND, полное совпадение команд, ARM выключен.

Результаты предыдущего прогона Windows SITL 4.7.3: [протокол SITL](../docs/sitl-validation.md). Проверка управления полётом описана ниже. Следующий вариант UDP полезен при использовании внешнего SITL/MAVProxy.

По умолчанию backend слушает `udpin:127.0.0.1:14550`, ожидая пакеты от ArduPilot, system=1/component=1. SITL/MAVProxy нужно настроить на отправку в этот адрес. Если порт уже использует другая наземная станция, назначьте backend отдельный выход, например 14551:

```powershell
$env:MAVLINK_ENDPOINT='udpin:127.0.0.1:14551'
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

В MAVProxy добавьте выход командой `output add 127.0.0.1:14551`. Для SITL внутри WSL адрес назначения может быть адресом Windows-хоста; настройки сети WSL нужно проверить отдельно. Бинарник SITL скачивается отдельно и не включается в Git.

Подключение определяется по HEARTBEAT именно заданного ArduPilot. Backend запрашивает потоки данных и HOME_POSITION. При отсутствии HEARTBEAT более 5 секунд связь становится неактивной, операция завершается ошибкой. Без свежих координат выводятся прочерки. Демо-данные никогда не подменяют данные MAVLink.

Настройки окружения:

| Переменная | По умолчанию |
|---|---|
| `MAVLINK_ENDPOINT` | `udpin:127.0.0.1:14550` |
| `MAVLINK_BAUD` | `115200` |
| `MAVLINK_SYSTEM_ID` | `1` |
| `MAVLINK_COMPONENT_ID` | `1` |
| `BRIDGE_DATABASE` | `backend/data/bridge.sqlite3` |
| `BRIDGE_ORIGINS` | localhost/127.0.0.1, порты 5173–5183 и 4173–4183 (включая запасные порты Vite) |
| `VITE_API_URL` (frontend) | `http://127.0.0.1:8000` |

## API

### Управление полётом

`POST /api/flight` принимает `{action, missionId?}`: `arm`, `disarm`, `start`, `rtl`, `land`. Возвращает HTTP 202 и обычную операцию с `operationId`. Команды проходят через единственного MAVLink worker. `succeeded` означает принятый COMMAND_ACK и наблюдаемое состояние ARM/режима; посадка и завершение полёта определяются отдельно по телеметрии.

Порядок в интерфейсе: загрузить план → проверить совпадение → «Подготовить к полёту (ARM)» → «Запустить миссию». Подготовка включает GUIDED (176), затем обычный ARM (400, param1=1, param2=0); запуск включает AUTO (176), затем MISSION_START (300). Нужны свежие GPS/Home и подтверждение, что аппарат на земле. Для запуска обязательны проверенный `missionId` и взлёт в начале плана. После выполненного запуска для нового полёта требуется повторная загрузка миссии. Принудительный ARM/DISARM не поддерживается, команды управления автоматически не повторяются при таймауте. «Выключить ARM» доступно только на земле. «Посадка здесь» меняет режим на LAND, «Возврат домой» — на RTL.

Статус содержит `currentSeq`, `missionCount` (без служебного Home), `reached`, `missionState`, `landedState`, `startConsumed`, `verifiedMissionId` и `lastText`. MISSION_ITEM_REACHED отмечает сообщённое автопилотом прохождение команды; это не подтверждение работы физической камеры. После переподключения проверку миссии нужно повторить. На карте зелёная линия показывает последние 2000 координат текущей сессии полёта; текущая и достигнутые точки подсвечиваются только при совпадении плана с проверенной миссией. След хранится в памяти браузера.

Проверка реального выполнения: [check_flight.py](tools/check_flight.py) предназначен только для отдельного SITL на `tcp:127.0.0.1:5770`, использует временную базу, заменяет тестовую миссию и запускает полёт. Для такого экземпляра используется [sitl_wsl.py](../tools/sitl_wsl.py) с `run --instance 1 --speedup 4`. Основной экземпляр и миссия в открытом интерфейсе не затрагиваются. Результат прогона сохраняется локально в `.runtime/flight-check.json`.

Протокол команд: [ARM/DISARM](https://ardupilot.org/dev/docs/mavlink-arming-and-disarming.html), [команды миссий ArduPilot](https://ardupilot.org/copter/docs/common-mavlink-mission-command-messages-mav_cmd.html).

| Запрос | Назначение |
|---|---|
| `GET /api/health` | Проверка сервера и статуса моста |
| `GET /api/status` | Связь, ARM, режим, Home, активная операция |
| `POST /api/missions` | Проверить и сохранить план v3; вернуть `missionId` и собранные `items` |
| `GET /api/missions` | Последние 100 сохранённых миссий |
| `GET /api/missions/{id}` | Получить сохранённую миссию и команды |
| `POST /api/uploads` | `{ "missionId": "…" }`; HTTP 202 означает только постановку в очередь |
| `POST /api/mission-checks` | `{ "missionId": "…" }`; прочитать миссию с борта и сравнить с сохранённым планом |
| `GET /api/operations/{id}` | `queued`, `running`, `succeeded` или `failed` |
| `POST /api/commands` | Отдельная команда: 20, 178, 115 или 203, с проверенными `params` |
| `WS /ws/telemetry` | События `status`, `telemetry`, `operation`, `mission_current` |

Команды ARM (400) и MISSION_START (300) на этом этапе не принимаются. Отдельные команды отправляются один раз и ждут соответствующий COMMAND_ACK; повторять неподтверждённый снимок автоматически нельзя. Вызов RTL (20) через API — реальная команда возврата подключённому борту.

Принимаемый план — `version=3`, `settings`, `waypoints`, необязательный `frame=GLOBAL_RELATIVE_ALT`. Поля `waypoints`, `actions`, `params`, `target` соответствуют экспортируемой структуре клиента. Клиентские `items` допустимы для совместимости, но сервер их не сохраняет и не отправляет: команды собираются заново из исходного плана. Проверяются типы, конечность чисел, диапазоны, поддерживаемые команды, количество точек и уникальность идентификаторов.

Для ArduPilot добавляется служебный Home в `seq=0`, поэтому TAKEOFF не теряется. Используются координаты/абсолютная высота из HOME_POSITION борта. Плановый Home сверяется с ним с допуском 20 м; отличие или Home старше 30 секунд блокируют загрузку. Backend не отправляет DO_SET_HOME.

Протокол: MISSION_COUNT → MISSION_REQUEST_INT → MISSION_ITEM_INT → MISSION_ACK. Повторные запросы поддерживаются; таймаут ответа 1,5 с, максимум 5 повторов, общее время операции 120 с. Ответ на старый MISSION_REQUEST также отправляется как MISSION_ITEM_INT. Источник, адресат и тип миссии проверяются. Успех фиксируется только после запросов всех элементов и MISSION_ACK с MAV_MISSION_ACCEPTED. Отрицательный ACK, неверный номер, потеря связи или таймаут дают ошибку. Предварительной очистки миссии нет. На ArduPilot загрузка не атомарна: после неудачи нельзя считать старую миссию сохранённой без проверки.

Телеметрия: GLOBAL_POSITION_INT (lat/lon ×10⁻⁷°, relative_alt мм→м, vx/vy см/с→м/с, hdg сотые градуса), SYS_STATUS (батарея), GPS_RAW_INT (спутники/fix), HEARTBEAT (режим/ARM). Неизвестные значения передаются как `null`. Время событий — Unix миллисекунды сервера.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests -q
npm test
npm run build
```

Есть проверки API, хранения, повторной компиляции, положительного/отрицательного/преждевременного ACK, таймаутов, Home, фильтрации сообщений, единиц телеметрии, WebSocket и реальных MAVLink 2 пакетов по локальному UDP. Тестовый UDP peer не является SITL. Дополнительно выполнен отдельный прогон на настоящем ArduPilot SITL: загрузка, чтение и сравнение двух миссий; проверены кнопки React и выявление расхождений. Следующий этап — ARM/START и проверка исполнения действий в симуляторе.

Чтение использует MISSION_REQUEST_LIST → MISSION_COUNT → MISSION_REQUEST_INT/ITEM_INT → MISSION_ACK. Оно выполняется той же очередью и тем же worker, не открывая второе MAVLink-соединение. Успешная операция возвращает `result.matches`, `result.differences` и прочитанные `result.items`. `succeeded` при `matches=false` означает успешное чтение отличающейся миссии. Отличие не скрывается как успешное совпадение.

Источники: [Mission Protocol](https://mavlink.io/en/services/mission.html), [pymavlink](https://mavlink.io/en/mavgen_python/), [FastAPI WebSockets](https://fastapi.tiangolo.com/advanced/websockets/).
